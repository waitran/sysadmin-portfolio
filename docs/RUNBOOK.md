# Runbook учебной лаборатории

Практикум предназначен для локального запуска через Docker Compose. Приложение: [localhost:8080](http://localhost:8080/healthz), Prometheus: [localhost:9090](http://localhost:9090). Порты привязаны к loopback. Выполняйте команды из корня репозитория на своей машине.

Инъекция ошибок включена в Compose через `ENABLE_FAULT_INJECTION=true`. Параметры `fail=1` и `delay_ms=600` нужны для упражнения; не переносите этот режим в публичный сервис.

## Запуск и проверка

```sh
make check-config
make test
make test-rules
make up
make smoke
make load
```

`/healthz` показывает, что процесс отвечает; `/readyz` — что приложение готово обрабатывать запросы. В этой простой лаборатории нет внешних зависимостей, поэтому readiness не проверяет базу данных или очередь.

В [Prometheus Targets](http://localhost:9090/targets) target `demo` должен быть `UP`. После старта дайте пройти минимум двум сборам метрик для расчёта скорости. В [Graph](http://localhost:9090/graph) проверьте:

```promql
demo:requests:rate5m
demo:errors:ratio5m
demo:latency:p95_5m
```

Нулевой трафик, короткий прогрев и перезапуск счётчиков влияют на графики. Для проверки порогов поддерживайте нагрузку; один короткий всплеск не гарантирует срабатывание алерта.

## Диагностика сигналов

| Сигнал | Что проверить | Действие |
| --- | --- | --- |
| `DemoServiceDown` | Targets, `make logs`, доступность `/healthz` и `/metrics` | Исправить причину запуска или сбора, затем `make up` и `make smoke` |
| `DemoHighErrorRate` | `demo:errors:ratio5m`, ответы `500`, наличие `fail=1` в тестовом трафике | Завершить инъекцию, запустить успешный трафик, проверить логи |
| `DemoHighLatency` | `demo:latency:p95_5m`, параметр `delay_ms`, загрузку локальной машины | Завершить инъекцию задержки и проверить успешный трафик |

`DemoServiceDown` означает проблему сбора метрик и сам по себе не доказывает пользовательский простой. Если графики исчезли, проверьте Prometheus и список targets: отсутствие данных тоже требует внимания.

## Ручное упражнение

1. Выполните запуск и проверки выше. Запишите время начала и исходные показатели.
2. Откройте [Alerts](http://localhost:9090/alerts). У алертов есть состояния `inactive`, `pending`, `firing`; поле `for` требует непрерывного выполнения условия.
3. Запустите `make chaos`: в течение 180 секунд каждый четвёртый запрос содержит `fail=1` и возвращает `500`. Для отдельной проверки задержки используйте `make latency`: в течение 180 секунд запросы `/api/work?delay_ms=600` выполняются медленно. Проводите сценарии по одному, с восстановлением между ними.
4. Во время сценария проверяйте фактическую скорость > 0,1/с и график условия. Прогрев и 5-минутное окно могут увеличить время до `firing`; при необходимости повторите команду.
5. После инъекции выполните `make recover`: 330 секунд успешного трафика, затем `make smoke`. Убедитесь, что обычный `/api/work` снова отвечает успешно.
6. Наблюдайте восстановление: старые ошибки и задержки остаются в окне до 5 минут плюс очередная проверка правил. `make recover` не стирает историю. Подтвердите возвращение алерта в `inactive`.

Для отдельного упражнения недоступности остановите только приложение:

```sh
docker compose stop demo
# После наблюдения DemoServiceDown:
make up
make smoke
```

Оставляйте Prometheus запущенным, иначе он не сможет показать алерт. На первичном старте и при изменении конфигурации возможны дополнительные задержки сбора. В лаборатории нет Alertmanager: состояние алертов видно в интерфейсе Prometheus, доставка уведомлений не настроена.

## Что приложить к разбору

- Коммит, версия Docker Compose, время и часовой пояс упражнения.
- Команды сценария и фактические ответы HTTP до, во время и после инъекции.
- Снимки графиков с интервалом времени, значениями и выражениями запросов.
- Переходы `pending` → `firing` → `inactive` либо объяснение, почему условие не выполнилось.
- Причина, способ восстановления и ограничения наблюдения без секретов и персональных данных.

Заполните [шаблон разбора](INCIDENT-TEMPLATE.md) только по фактическим результатам. Учебная инъекция не является доказательством коммерческого опыта.

После практики остановите лабораторию: `make down`. Логи доступны через `make logs`.
